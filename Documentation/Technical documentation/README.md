# Техническая документация

Описание предназначено для настройки интеграции и сопровождения клиента. Начать работу помогает [инструкция по установке](setup.md); правила обращения с локальными данными и публикации находятся в [разделе конфиденциальности](security.md).

## Устройство

В [скилле](../../skills/jira-workflow/SKILL.md) находятся правила выбора задачи, согласования действий и работы с файлами. [Точка входа клиента](../../client/jira.ps1) проверяет регистрацию рабочего репозитория до чтения токена и сетевых запросов, подключает модули и возвращает JSON. Исключение — отдельно запрошенная команда `GetProjects`: она только проверяет аккаунт и показывает доступные проекты без чтения конфигурации, записи состояния и запуска очистки.

| Компонент | Ответственность |
| --- | --- |
| `JiraApi.psm1` | Авторизация, разрешённые REST-ресурсы, пагинация, ADF и потоковое скачивание |
| `JiraStorage.psm1` | Привязки репозиториев, разделение данных по аккаунтам, блокировка, атомарная запись и очистка |
| `JiraOperations.psm1` | Получение задач, вложения, подготовка, выполнение и сверка операций |
| `JiraIssueChanges.psm1` | Пошаговое создание со связями и файлами, отдельные связи/вложения, текстовые комментарии и дополнение описания, сохранение ADF и сверка каждого шага |

Клиент определяет корень по своему расположению: родительская папка `client/`. Там находятся `config.json` и создаваемая при работе папка `data/`. Путь AppData не используется. Настройка установленного скилла отдельно сообщает агенту, где лежит этот репозиторий.

## Команды

Все команды, кроме `GetProjects`, требуют `-RepositoryPath` с абсолютным путём зарегистрированного рабочего репозитория или его подпапки. Это не путь к клиенту.

| Команда | Назначение |
| --- | --- |
| `GetProjects` | Проверить авторизацию и показать ID, ключи и названия доступных проектов без привязок, конфигурации и локальных записей |
| `GetIssue` | Задача, доступные комментарии, локальный снимок; `-WithAttachments` добавляет скачивание вложений |
| `DownloadAttachments` | Вложения задачи, при необходимости только указанные ID |
| `GetTransitions` | Текущий статус и актуальные доступные переходы |
| `GetCatalog` | Справочники разрешённых проектов; `-Refresh` обновляет их принудительно |
| `GetCreateFields` | Актуальные обязательные и доступные поля создания |
| `GetLinkTypes` | Актуальные типы связей и подписи обоих направлений |
| `LogWorklog` | Подготовка и выполнение уже согласованного списания за один запуск; обязательны UUID операции, JSON параметров и `-Confirmed` |
| `PrepareWorklog`, `PrepareTransition`, `PrepareIssue` | Подготовка неизменяемого предложения с UUID и хешем запроса |
| `PrepareLink`, `PrepareAttachments` | Подготовка связей либо загрузки файлов в описание/новый комментарий; `PrepareIssue` также принимает связи и файлы |
| `PrepareDescription` | Подготовка дополнения описания текстом или вставки текста и уже встроенного изображения |
| `PrepareComment` | Подготовка нового текстового комментария без вложений и изменения описания |
| `PrepareImageComment` | Подготовка нового комментария со встроенным изображением из вложений задачи |
| `Execute` | Выполнение подготовленного и согласованного предложения |
| `GetOperation` | Просмотр локальной операции |
| `Reconcile` | Проверка результата ранее отправленного запроса |
| `Cancel` | Отмена только локального предложения, которое ещё не отправлялось |

Результат содержит `ok`, `command`, `cleanedOperations`, `cleanedArtifacts` и `data`. При ошибке клиент выводит краткий JSON в stderr и завершает процесс с кодом 1. Параметры и примеры JSON приведены в [справочнике клиента](../../skills/jira-workflow/references/client-usage.md).

### Дополнение описания без вложений

Для текстового дополнения `PrepareDescription` принимает UTF-8 JSON с ключом задачи и непустым текстом:

```json
{
  "issueKey": "EXAMPLE-13",
  "text": "Краткое описание бизнес-логики задачи."
}
```

```powershell
pwsh -NoProfile -File '<clientRepositoryPath>/client/jira.ps1' -Command PrepareDescription -RepositoryPath '<registeredRepositoryPath>' -PayloadPath '<absolutePathToRequest.json>'
pwsh -NoProfile -File '<clientRepositoryPath>/client/jira.ps1' -Command Execute -RepositoryPath '<registeredRepositoryPath>' -OperationId '<id>' -RequestHash '<requestHash>' -Confirmed
```

Первая команда читает задачу и сохраняет предложение с UUID, хешем, исходным описанием и текстом. Она не меняет Jira. После просмотра и согласования выполняется `Execute` с теми же ID и хешем. Описание дополняется абзацами, прежние ADF-узлы и оформление сохраняются; вложения и отдельные комментарии не создаются, другие поля задачи не изменяются. Пустой/пробельный текст и посторонние свойства запроса отклоняются.

Если описание изменилось после подготовки, запись останавливается до PUT: нужно прочитать актуальный текст и подготовить новое согласованное дополнение. Как и для дополнения с вложениями, проверка не является серверной блокировкой: изменение между последним GET и PUT остаётся ограничением Jira API. Неизвестный исход проверяется через `Reconcile` с прежним UUID; повтор завершённой операции не отправляет PUT заново. `rendering: text` в результате отличает этот сценарий от загрузки файлов.

При проверке описания отсутствие `content` у пустого абзаца эквивалентно `content: []`: Jira может возвращать такую форму после сохранения. Остальные ADF-узлы, текст, атрибуты и оформление сравниваются полностью. Нормализация применяется только к сравнению описаний и тел комментариев; хеш согласованного запроса и журнал не меняются.

### Изображения в описании

В `PrepareDescription` можно указать `attachmentId`, например `{"issueKey":"EXAMPLE-13","attachmentId":"10001","text":"Результат проверки"}`. В описании должен быть единственный встроенный блок с именем выбранного файла. Клиент сохранит существующие блоки и вставит текст и изображение сразу после найденного блока. Изображение сохраняет исходные пропорции и выравнивается слева. Ширина блока равна 100% доступной ширины описания.

С `resizeExisting: true` клиент использует `text` для поиска подписи сразу над выбранным изображением и меняет его выравнивание и ширину на месте. Подпись и остальные блоки описания сохраняются.

При создании задачи `PrepareIssue` принимает `attachments` с `files`, `placement: "description"` и `rendering: "inline-images"` вместо режима ссылок. Поддерживаются PNG, JPEG и GIF с уникальными именами и исходными размерами, прочитанными из файла. После создания задачи с отметкой операции и загрузки файлов клиент вставляет wiki-изображения через API v2, сверяет полученные Media ID и публикует согласованное описание через API v3. До завершения в описании может отображаться отметка операции. Если публикация остановилась, состояние и утверждённое описание остаются в журнале. Отдельный комментарий при этом не создаётся.

### Отдельный текстовый комментарий

`PrepareComment` принимает JSON с `issueKey` и непустой строкой `text`, как `PrepareDescription`, но готовит один новый комментарий. Подготовка только читает задачу и записывает локальную операцию. После согласования `Execute` с прежними UUID и хешем отправляет `POST issue/{key}/comment`; описание и остальные поля не изменяются, файлы не загружаются. `rendering: text` явно обозначает текст без вложений.

В тело комментария добавляется отдельный абзац `Операция: <UUID>`. При обрыве связи `Reconcile` сверяет все страницы комментариев, полный маркер, автора и точное содержимое ADF с учётом нормализации пустых абзацев. Если совпадений нет, их несколько или содержимое изменилось, состояние остаётся `unknown`; повторный POST запрещён. Завершённая операция возвращает прежний результат без дубликата. Формат запроса и команды приведены в [справочнике клиента](../../skills/jira-workflow/references/client-usage.md#отдельный-текстовый-комментарий).

### Изображение в комментарии

`PrepareImageComment` принимает `-PayloadPath` с UTF-8 JSON, например `{"issueKey":"EXAMPLE-13","attachmentId":"10001"}`. Вложение должно быть изображением с уникальным именем в этой задаче. Предложение показывает имя, размер и ID файла. `Execute` с согласованным UUID и хешем добавляет один комментарий через REST API v2 с wiki-разметкой `!имя.png!` и маркером операции. Jira определяет размер отображения.

Клиент читает комментарий через API v3 и возвращает `inlineImages: true`, если Jira сохранила встроенный блок изображения. При `inlineImages: false` комментарий найден, а отображение картинки не подтверждено. `Reconcile` сверяет маркер и автора, затем проверяет наличие блока изображения без повторной отправки. [Jira REST API v2](https://developer.atlassian.com/cloud/jira/platform/rest/v2/api-group-issue-comments/#api-rest-api-2-issue-issueidorkey-comment-post)

Чтобы сохранить размер и выравнивание, укажи `sourceCommentId`, например `{"issueKey":"EXAMPLE-13","attachmentId":"10001","sourceCommentId":"20001"}`. Исходный комментарий должен быть доступен без ограничения видимости, принадлежать авторизованному аккаунту и содержать встроенное изображение с именем выбранного вложения. Предложение показывает исходный комментарий и параметры изображения. При отправке через REST API v3 клиент сверяет исходный блок и переносит его Media ID, ширину и выравнивание. `layoutMatched: true` подтверждает совпадение параметров в сохранённом комментарии. [Jira REST API v3](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issue-comments/#api-rest-api-3-issue-issueidorkey-comment-post)

## Правила действий

Задача выбирается по прямому указанию, затем по текущей ветке и относящимся к работе коммитам. Сам скилл не даёт общего разрешения запускать команды Git. При нескольких подходящих задачах требуется уточнение.

Перед списанием агент согласует задачу, продолжительность, начало и описание работы. Прямая однозначная команда на списание также считается согласием. Подтверждение конкретного списания разрешает запуск клиента для этого списания без второго вопроса о запуске скрипта. Оценка длительности работы приблизительная; неизвестное время нельзя вычислять с выдуманной точностью по переписке.

Комментарий worklog начинается с `[Codex]` и содержит полный UUID операции. `adjustEstimate=auto` уменьшает оставшуюся оценку; первоначальная оценка не меняется. Автор записи — владелец API token. Требования Jira к правам и включённому учёту времени описаны в [Add worklog](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issue-worklogs/#api-rest-api-3-issue-issueidorkey-worklog-post).

Перед сменой статуса клиент получает доступные переходы и проверяет их снова перед отправкой. ID статуса и ID перехода различаются. Если выбранный переход пропал, агент показывает актуальные варианты и ждёт решения. Создание задачи требует показа проекта, типа, содержания и обязательных полей с последующим явным подтверждением. Удаление, массовые изменения и администрирование не поддерживаются.

## Повторные запросы

Связи создаются отдельным `POST issueLink` с проверкой типа, направления и обеих задач. Файлы загружаются отдельными multipart-запросами; ссылки публикуются новым комментарием или дополнением описания через PUT. Старые ADF-узлы сохраняются, изменение описания после подготовки останавливает отправку. По умолчанию вложения существующей задачи идут в комментарий; описание выбирается явно.

`PrepareAttachments` требует явный `rendering: links`. Вставку в описание или комментарий выполняют отдельные режимы. [Изображения в описании](#изображения-в-описании) · [Изображение в комментарии](#изображение-в-комментарии)

Такая операция хранит результаты каждого шага. `partial` позволяет продолжить прежний план без повторения выполненного; `unknown`/`sending` запрещает продолжение до сверки. `Reconcile` проверяет только результат, не отправляет остальные шаги. Загрузка сверяется по новым ID относительно сохранённого списка, автору, имени, размеру и SHA-256; комментарий — по UUID, автору и ADF. При неоднозначности повтор запрещён. Общей транзакции и автоматического удаления результатов при сбое нет.

Подготовка сохраняет точные параметры и хеш, но не изменяет Jira. Перед отправкой клиент сохраняет состояние `sending`. При неопределённом результате запрещено слепо повторять запрос или создавать новое предложение для обхода проверки: сначала используется `Reconcile`.

`LogWorklog` объединяет эти этапы для уже согласованного списания: один запуск PowerShell и четыре HTTP-запроса вместо двух запусков и пяти запросов через `PrepareWorklog`/`Execute`. UUID задаётся до запуска; повтор с тем же UUID и параметрами использует прежнюю запись журнала. Завершённое списание не отправляется повторно, изменённые параметры отклоняются, неопределённый результат требует сверки. Для уже подготовленного предложения сохраняется `Execute` с его ID и хешем.

Проверки задач получают только используемые поля, например проект, название или статус. [Параметр `fields` Jira](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issues/#api-rest-api-3-issue-issueidorkey-get) ограничивает состав ответа. Полный просмотр через `GetIssue` сохраняет все доступные поля, все страницы комментариев и прежнюю работу с вложениями.

Журнал и маркеры помогают обнаружить уже выполненное действие, но не обеспечивают серверную идемпотентность Jira. При неоднозначном результате клиент останавливается. Флаг `-Confirmed` сам по себе не доказывает согласие человека: его проверяет агент по переписке.

## Кеш и очистка

Данные разделяются внутри `data/<хеш сайта и Cloud ID>/<хеш accountId>/`. Во время команды удерживается эксклюзивная блокировка аккаунта.

| Данные | Хранение и обновление |
| --- | --- |
| Проекты, типы задач, статусы | Обновление при обращении после 24 часов или по запросу |
| Снимки задач и вложения | 30 дней без использования через клиент; проверка не чаще раза в 24 часа |
| Завершённые, окончательно неудачные и отменённые операции | 90 дней после завершения; чистка при первом обращении в новом месяце по UTC |
| Незавершённые операции и неизвестный результат | Автоматически не удаляются |

Ручное открытие файла в Проводнике срок хранения не продлевает. Без запуска клиента чистка откладывается. Удаляются только соответствующие локальные копии; данные Jira не удаляются.

Вложения кешируются по задаче и ID с проверкой размера и SHA-256. Каждое новое скачивание строго больше 500 000 000 байт требует отдельного согласия на конкретный файл. Ровно 500 МБ дополнительного согласия не требует. Скачивание не означает, что агент уже прочитал файл.

## Проверка подключения

После настройки начать с чтения одной зарегистрированной задачи. Успешное чтение не подтверждает права на списание, создание или переходы: они зависят от настроек Jira. Изменяющие операции проверяются только по отдельной согласованной команде.

Локальный тестовый набор использует заглушку HTTP и отдельное хранилище; он исключён из публикации вместе с `client/tests/`. Если набор присутствует локально, его запуск требует применимого разрешения. Статическая проверка и такие тесты не заменяют проверку реального подключения.
