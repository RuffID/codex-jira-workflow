# Локальный клиент Jira

Точка входа: `<clientRepositoryPath>/client/jira.ps1`. Путь определяется по разделу «Найти локальный клиент» в `SKILL.md`; фиксированного пути по умолчанию нет. В примерах `$jiraRoot` — проверенный абсолютный путь из локальной настройки скилла, `$jiraClient = Join-Path $jiraRoot 'client/jira.ps1'`. Эти переменные не заменяют обязательную проверку пути и регистрации.

Нужен PowerShell 7.5+ (`pwsh`), без установки дополнительных пакетов. Используй найденный установленный `pwsh`, а не Windows PowerShell 5.1; проверь доступность через `Get-Command pwsh` или известный путь установленного runtime.

Все команды, кроме `GetProjects`, требуют `-RepositoryPath` с абсолютным путём к зарегистрированному репозиторию или его подпапке. Клиент никогда не регистрирует проекты сам. При прямом запросе Jira без привязки агент сначала получает проекты через `GetProjects`, показывает полный путь рабочего репозитория и запрашивает выбор. Этот выбор разрешает агенту сохранить привязку в конфигурации и продолжить исходную операцию по её правилам подтверждения. Для остальных команд пустая конфигурация останавливает клиент до чтения токена и HTTP-запросов. Примеры ниже не разрешают их выполнение и не являются действующими привязками.

## Окружение

| Переменная | Значение |
| --- | --- |
| `JIRA_SITE_URL` | `https://<сайт>.atlassian.net`, без дополнительного пути |
| `JIRA_EMAIL` | Email владельца токена |
| `JIRA_API_TOKEN` | API token, вводится пользователем локально |
| `JIRA_CLOUD_ID` | UUID сайта для токена со scopes; запросы идут через `api.atlassian.com/ex/jira/{cloudId}` |

Без `JIRA_CLOUD_ID` клиент использует адрес сайта для обычного токена без scopes. Клиент не определяет вид токена по его содержимому. Для scoped-токена требуется правильный Cloud ID; не подменяй его ID организации.

Не читай и не печатай значения токена для диагностики. Передача токена аргументом, дамп окружения, логирование Authorization и запись секрета в JSON запрещены. Переменные окружения не являются защитой от чтения локальным процессом. Настройку пользовательского окружения выполняй только по отдельной просьбе; создание клиента не разрешает её автоматически.

Токену необходимы права на используемые endpoints, включая чтение текущего пользователя (`myself`). Подбирай scopes по официальным страницам конкретных методов. Не выдавай административные или delete-scopes ради удобства. Ограничения scopes не заменяют регистрацию репозитория и подтверждение операции.

## Показать проекты без регистрации

По прямому запросу показать проекты, проверить подключение либо выполнить операцию Jira для репозитория без привязки:

```powershell
& pwsh -NoProfile -File $jiraClient -Command GetProjects
```

Команда принимает только `-Command GetProjects`, проверяет аккаунт через `myself` и получает все страницы `GET project/search?orderBy=key`. В `data` находятся `projects` с полями `id`, `key`, `name` и `count`. Конфиг, кеш, журнал и данные не читаются и не изменяются; очистка не запускается. Команда работает и без `config.json`. Показ проектов не является регистрацией и не разрешает работать с их задачами. Дополнительные параметры отклоняются до чтения окружения и HTTP. Остальные команды сохраняют обязательную проверку регистрации.

Метод Jira: [Get projects paginated](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-projects/#api-rest-api-3-project-search-get).

## Чтение

```powershell
& pwsh -NoProfile -File $jiraClient -Command GetIssue -RepositoryPath 'D:\Work\ExampleRepository' -IssueKey 'EXAMPLE-13' -WithAttachments
```

Результат JSON содержит `ok`, `command`, `cleanedOperations`, `cleanedArtifacts` и `data`. Для задачи в `data` возвращаются ключ, название, статус, ссылка, пути `snapshotPath` и `textPath`, список вложений и `downloads` с путями файлов/манифеста. Исходный JSON сохраняет все доступные поля задачи и все доступные комментарии; файлы не исполняются и не распаковываются. `cleanedArtifacts` содержит признак выполнения проверки, количество удалённых файлов/каталогов и освобождённые байты.

Остальные команды чтения:

- `GetIssue` без `-WithAttachments`: сохранить данные задачи и комментарии, только перечислить вложения.
- `DownloadAttachments -IssueKey <ключ>`: скачать все вложения задачи. Для выбора добавить `-AttachmentIds '10001','10002'` при вызове из PowerShell; при запуске нового процесса с `-File` передача нескольких значений массива зависит от оболочки — для отдельных ID безопаснее отдельные вызовы.
- `GetTransitions -IssueKey <ключ>`: текущий статус, актуальные переходы и поля переходов.
- `GetCatalog`: справочники только разрешённых проектов, кеш на 24 часа. `-Refresh` обновляет принудительно и не меняет привязки репозиториев.
- `GetCreateFields -ProjectKey <ключ проекта> -IssueTypeId <ID>`: свежие метаданные полей создания.
- `GetOperation -OperationId <UUID>`: состояние и согласованные параметры операции.

Вложения кешируются по ключу задачи и ID. Перед повторным использованием проверяются имя, размер и SHA-256 файла. В `files` есть признак `reused`; повторная загрузка целой копии не выполняется, отметка использования продлевается. Повреждённая/неподходящая копия заменяется проверенным скачиванием.

Для каждого нового скачивания больше 500 МБ (500 000 000 байт) клиент возвращает элемент `skipped` с ID, именем, размером, `reason: confirmation-required` и `thresholdBytes`, без запроса содержимого. В `GetIssue` это поле находится в `data.downloads.skipped`, в `DownloadAttachments` — в `data.skipped`. Покажи эти данные и дождись согласия. После согласия на конкретный файл:

```powershell
& pwsh -NoProfile -File $jiraClient -Command DownloadAttachments -RepositoryPath 'D:\Work\ExampleRepository' -IssueKey 'EXAMPLE-13' -AttachmentIds '10001' -ApprovedLargeAttachmentIds '10001'
```

`-ApprovedLargeAttachmentIds` применяется только к выбранным ID, а не ко всем файлам задачи. Не передавай его без явного согласия на показанный файл. Файл ровно 500 МБ не требует дополнительного согласования. Целая уже скачанная копия используется без нового запроса содержимого даже при размере больше порога. Если она повреждена и требуется новое скачивание, согласие снова необходимо.

Для операций с задачами и справочниками конкретного рабочего репозитория ключ проекта должен присутствовать в привязке. Это не требуется для отдельного показа проектов через `GetProjects`. Если Jira вернула другой ключ задачи, клиент останавливается: не принимай перенаправление старого ключа за согласие на другую задачу.

## Списание времени

В разрешённой рабочей папке создай UTF-8 JSON запроса (не в репозитории без необходимости):

```json
{
  "issueKey": "EXAMPLE-13",
  "timeSpentSeconds": 600,
  "started": "2026-11-13T09:00:00+07:00",
  "description": "Исправление расчёта"
}
```

Дата в примере не является текущей датой. Используй явно указанные пользователем начало/период и явный часовой пояс. Если прямая команда задаёт только продолжительность, по согласованному правилу получи текущее время и вычти эту продолжительность для `started`, без вопроса о начале и без повторного подтверждения списания. Это условная отметка начала, а не измерение рабочего времени. Явно указанную дату или период не подменяй текущим. Вычисленное начало зафиксируй до подготовки: при сбое и проверке результата не пересчитывай его и не создавай новый запрос для обхода неизвестного результата. Исходная продолжительность — целое число секунд, больше нуля. Округление не выдумывай, итог согласуй, если продолжительность ещё не задана.

### Уже согласованное списание за один запуск

Если все параметры согласованы или заданы прямой однозначной командой, используй `LogWorklog`. До запуска создай UUID и сохрани его в контексте вместе с неизменным JSON. Команда требует `-OperationId`, `-PayloadPath` и `-Confirmed`:

```powershell
$worklogOperationId = [guid]::NewGuid().ToString('D') # Только для новой операции; сохранить до запуска.
& pwsh -NoProfile -File $jiraClient -Command LogWorklog -RepositoryPath 'D:\Work\ExampleRepository' -PayloadPath 'C:\Work\worklog-request.json' -OperationId $worklogOperationId -Confirmed
```

Клиент сохраняет подготовленный запрос и хеш, проверяет задачу перед POST и записывает `sending` до отправки. Для нового списания используются один процесс, одна авторизация `myself`, две проверки задачи с нужными полями и один POST. Результат в `data` — обычная запись операции с `id`, `requestHash`, `status` и `result`.

При повторе используй прежний UUID и тот же JSON, не выполняй генерацию UUID заново. Завершённая операция возвращает сохранённый результат без повторного POST; другие параметры с тем же UUID отклоняются. Состояния `sending` и `unknown` требуют `Reconcile`; новый UUID не является способом повторить запрос. Неопределённый результат и прежнее начало списания сохраняются. Хранение UUID в контексте не заменяет локальный журнал.

### Предложение, ожидающее подтверждения

```powershell
& pwsh -NoProfile -File $jiraClient -Command PrepareWorklog -RepositoryPath 'D:\Work\ExampleRepository' -PayloadPath 'C:\Work\worklog-request.json'
```

`PrepareWorklog` читает задачу и сохраняет локальную операцию `prepared`, не отправляя POST. Клиент сам добавляет `[Codex]` и полный UUID в комментарий. Результат содержит `id`, `requestHash`, `preview` и сериализованный `requestJson`. Покажи пользователю понятные данные из `preview`, сохрани связь с точными ID/хешем. Списание использует `adjustEstimate=auto`, первоначальная оценка не меняется.

После разрешения конкретной операции:

```powershell
& pwsh -NoProfile -File $jiraClient -Command Execute -RepositoryPath 'D:\Work\ExampleRepository' -OperationId '<UUID>' -RequestHash '<хеш из подготовленного предложения>' -Confirmed
```

Флаг `-Confirmed` передаёт решение агента, но не доказывает человеческое согласие сам по себе. Проверка согласия остаётся обязанностью скилла. Клиент не знает переписку. Нельзя менять согласованные параметры и подставлять новый хеш без нового согласования.

## Переход и создание

`PrepareTransition` принимает JSON:

```json
{
  "issueKey": "EXAMPLE-13",
  "transitionId": "21",
  "fields": {}
}
```

Сначала узнай ID из `GetTransitions`; ID статуса не заменяет ID перехода. Клиент проверяет поля и сохраняет исходный/целевой статус. Перед POST переход проверяется снова. Изменение исходного статуса или недоступный переход требуют нового решения. Если целевой статус уже достигнут, повторного перехода нет.

`PrepareIssue` принимает `fields` и необязательные `links`/`attachments`:

```json
{
  "fields": {
    "project": { "key": "EXAMPLE" },
    "issuetype": { "id": "10001" },
    "summary": "Название задачи",
    "description": "Подготовленное описание"
  }
}
```

ID типа бери из актуального каталога, поля — из `GetCreateFields`. Дополнительные поля допускаются только с экрана создания; для дочерней задачи нужен согласованный `parent.key` из того же проекта. Строковое `description` преобразуется в ADF; многострочные пользовательские поля при необходимости передавай в формате, указанном метаданными. Клиент не выполняет создание с `update`, произвольным переходом или другими скрытыми действиями. В запрос добавляется property `codex.operation` с UUID для проверки результата после обрыва связи.

После показа конкретных данных и явного согласия создание/переход выполняются той же командой `Execute`. `Cancel -OperationId <UUID>` отменяет только локальную подготовленную и ещё не отправленную операцию; это не отмена изменений Jira.

## Связи задач

`GetLinkTypes` возвращает актуальные `issueLinkTypes` с `id`, `name`, `inward`, `outward`:

```powershell
& pwsh -NoProfile -File $jiraClient -Command GetLinkTypes -RepositoryPath 'D:\Work\ExampleRepository'
```

`PrepareLink` принимает JSON:

```json
{
  "issueKey": "EXAMPLE-13",
  "links": [
    { "issueKey": "EXAMPLE-14", "typeId": "10000", "direction": "outward" }
  ]
}
```

Здесь и ниже ключи и ID вымышлены: тип выбирается из фактического `GetLinkTypes`. `direction` задаёт подпись на основной задаче: `outward` соответствует `type.outward`, `inward` — `type.inward`. Например, для типа Blocks с outward=blocks основная задача блокирует указанную. Клиент сверяет обе задачи и проекты, запрещает связь с собой, проверяет актуальность типа перед POST и пропускает существующую связь. Для симметричного типа одинаковая связь в обратном направлении тоже считается существующей.

```powershell
& pwsh -NoProfile -File $jiraClient -Command PrepareLink -RepositoryPath 'D:\Work\ExampleRepository' -PayloadPath 'C:\Work\link-request.json'
```

Для создания со связями добавь такой же массив `links` рядом с `fields` в запрос `PrepareIssue`. Используется отдельный `POST issueLink` для каждой связи после создания, без ограничения поля linked issues на экране создания. Клиент не поддерживает удаление или замену существующих связей.

## Загрузка файлов и картинок

`PrepareAttachments` принимает:

```json
{
  "issueKey": "EXAMPLE-13",
  "files": ["C:\\Work\\screenshot.png", "C:\\Work\\details.pdf"],
  "placement": "comment",
  "text": "Материалы проверки",
  "rendering": "links"
}
```

```powershell
& pwsh -NoProfile -File $jiraClient -Command PrepareAttachments -RepositoryPath 'D:\Work\ExampleRepository' -PayloadPath 'C:\Work\attachments-request.json'
```

- `files` — непустой массив абсолютных путей существующих файлов. Подготовка фиксирует имена, размеры и SHA-256; выполнение перепроверяет содержимое. Файл открыт без разрешения записи до завершения отправки.
- `placement` по умолчанию `comment` для существующей задачи. Это новый комментарий, не изменение прежнего. Значение `description` явно выбирает дополнение описания. `text` необязателен.
- `rendering: "links"` обязателен: файлы, включая картинки, загружаются как вложения, а в описании/комментарии появляются кликабельные ссылки по attachment ID. Отображение изображения прямо внутри текста **не реализовано**. Другой режим отклоняется до загрузки; агент обязан сообщить различие до согласования.
- Перед загрузкой читается `GET attachment/meta`: вложения должны быть включены, каждый файл должен укладываться в фактический `uploadLimit`. Нужны права Browse Projects/Create attachments, а также Add comments либо Edit issues для выбранного размещения. Scoped-токену нужны соответствующие права по документации endpoints.
- Multipart-запрос содержит часть `file` и `X-Atlassian-Token: no-check`. Используется текущая API-база, включая Cloud ID для scoped-токенов. Авторизация на редиректы не передаётся.
- Описание дополняется новыми ADF-узлами; его исходные media/table/marks не заменяются текстом. Перед отправкой проверяется, что описание не изменилось после подготовки; при конфликте нужна новая подготовка и согласование. Эта проверка не является серверной блокировкой: одновременная правка между последним GET и PUT остаётся ограничением Jira API.

Для создания с файлами добавь `attachments` рядом с `fields`:

```json
{
  "fields": {
    "project": { "key": "EXAMPLE" },
    "issuetype": { "id": "10001" },
    "summary": "Название задачи",
    "description": "Основное описание"
  },
  "attachments": {
    "files": ["C:\\Work\\screenshot.png"],
    "text": "Материалы к задаче",
    "rendering": "links"
  },
  "links": [
    { "issueKey": "EXAMPLE-13", "typeId": "10000", "direction": "outward" }
  ]
}
```

Внутри `attachments` при создании `placement` по умолчанию `description`; можно явно выбрать `comment`. Весь план виден в `preview`: поля, файлы с размерами/хешами, типы и направления связей, место и текст публикации, `inlineImages: false`. Согласование не должно представлять ссылки как встроенные скриншоты. UUID/хеш подтверждаются обычным `Execute`.

Порядок шагов: создание (если нужно) → загрузка каждого файла → дополнение описания или новый комментарий → каждая связь. Это несколько отдельных запросов, без общей транзакции. Обратного удаления при сбое нет. Старые запросы `PrepareIssue` только с `fields` сохраняют прежнее поведение и формат журнала.

Документация: [связи](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issue-links/), [модель направлений](https://developer.atlassian.com/cloud/jira/platform/issue-linking-model/), [вложения](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issue-attachments/), [комментарии](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issue-comments/), [открытое ограничение Media ID](https://jira.atlassian.com/browse/CLOUD-12467). API v2/wiki и извлечение Media ID из внутренних URL этим клиентом не используются.

## Неизвестный результат

Клиент сохраняет `sending` до POST. HTTP-ошибка с однозначным отказом даёт `failed`; тайм-аут, сбой чтения успешного ответа или незавершённая проверка дают `unknown`. После аварийного завершения запись может остаться `sending`: она тоже требует проверки, повторный `Execute` запрещён. Завершённая операция возвращает прежний результат без повторного POST.

Используй `Reconcile -OperationId <UUID>`:

- Для списания проверяются все страницы worklog: полный маркер, автор, продолжительность, начало и комментарий. Отсутствие совпадения не является доказательством отсутствия записи; при нуле или нескольких совпадениях повтор автоматически запрещён.
- Для перехода проверяется фактически наблюдаемый целевой статус; это не доказательство, кто выполнил переход. Исходный POST не повторяется.
- Для создания укажи дополнительно `-ResultIssueKey <ключ предполагаемой созданной задачи>`: проверяется проект и UUID в property. Если ключ неизвестен, требуется выяснить его; автоматического повторного создания нет.

Для новых сценариев `requestJson.kind = issueWorkflow`. Неизменяемый план находится в `requestJson.steps`; результаты отдельных шагов — в `progress`. Состояние `sending` сохраняется перед каждым POST/PUT.

- При однозначном отказе шага он остаётся `pending`, операция — `partial`. Выполненные шаги сохраняются, незавершённая операция не удаляется по сроку хранения. После устранения причины прежний `Execute` продолжает только оставшиеся шаги с теми же UUID и хешем.
- При потере ответа/ошибке проверки шаг и операция становятся `unknown`; повторный `Execute` запрещён. После аварии `sending` также требует `Reconcile`.
- Создание сверяется по кандидату `ResultIssueKey` и property с UUID. Связь — по фактически наблюдаемому типу/направлению. Комментарий — по полному UUID в тексте, автору и точному ADF. Дополнение описания — по полному ожидаемому ADF, без утверждения авторства изменения.
- Для загрузки перед POST фиксируется список прежних attachment ID. Сверка проверяет новые ID, автора, имя, размер и SHA-256 скачанного содержимого. При нуле или нескольких подходящих файлах результат остаётся неизвестным; старый файл с таким же именем не заменяет результат загрузки.
- Успешная сверка даёт `partial`, если есть оставшиеся шаги, либо `completed`, если завершены все. `Reconcile` не отправляет оставшиеся изменения; для продолжения используется прежний согласованный `Execute`. После подтверждённой загрузки локальный исходник больше не требуется для публикации ссылки.

Не создавай новое предложение с теми же параметрами ради обхода неизвестного результата предыдущей операции. Не повторяй уже созданную задачу, загрузку или комментарий и не удаляй результаты частично выполненного плана автоматически. Нельзя считать ошибку HTTP-авторизации устаревшим справочником.

## Хранение

Конфигурация находится в `<clientRepositoryPath>/config.json`, `repositories` заполняется только по явному согласованию. Клиент определяет корень как родительскую папку своего `client/`, хранит данные в `<clientRepositoryPath>/data/` и не обращается к прежней папке AppData. Клиент конфиг не изменяет. Локальная настройка пути скилла не регистрирует рабочие репозитории.

Данные разделены по хешам сайта/Cloud ID и фактического `accountId` в `data\<сайт>\<аккаунт>\`. Внутри находятся `cache.json`, `operations\`, `snapshots\`, `downloads\`, `maintenance.json`, `artifact-maintenance.json` и файл блокировки. Блокировка удерживается на время команды; конкурентный вызов кратко сообщает занятость, не удаляя блокировку другого процесса. После завершения процесса файловый дескриптор освобождается системой.

Раз в календарный месяц по UTC, при первом обращении, удаляются только завершённые записи журнала старше 90 дней. Незавершённые, `sending` и `unknown` сохраняются. Конфигурация и данные Jira этой чисткой не затрагиваются.

Вложения находятся в `downloads\<ключ задачи>\<ID вложения>\`: файл, `attachment.json` с метаданными/контрольной суммой и `usage.json` с последним использованием. Общий `downloads\<ключ задачи>\manifest.json` содержит результат последнего обращения. Снимки находятся в `snapshots\<ключ задачи>\<UUID>\`, тоже с `usage.json`.

При запуске клиента проверяется отдельный срок хранения снимков/вложений: 30 дней без использования через клиент. Проверка выполняется не чаще раза за 24 часа. Повторная выдача вложения обновляет `lastUsedAt`; новый снимок получает эту отметку при создании. Ручное чтение локального файла вне клиента не отслеживается. Если клиент не запускался, чистка откладывается до следующего обращения. Для старых каталогов прежнего формата без `usage.json` срок считается от последней записи файлов/каталога. При повреждённых метаданных или reparse points чистка останавливается, а не выбирает другой путь удаления.

Удаление ограничено собственными подкаталогами `downloads` и `snapshots` текущего сайта/аккаунта. Перед удалением проверяется всё дерево и границы абсолютных путей. Копии в других каталогах, конфигурация, журнал и данные Jira не удаляются. Удаление локальной копии не мешает позднее скачать вложение из Jira снова.

## Проверка

Изолированный набор: `<clientRepositoryPath>/client/tests/JiraClient.Tests.ps1`. Его запуск требует отдельного разрешения по правилам пользователя; разрешение на обычное списание не распространяется на тестовый harness. Разрешение на команду со старым абсолютным путём не переносится на новый путь автоматически. Тесты заменяют HTTP-транспорт, не читают настоящие секреты/конфиг и сохраняют артефакты в собственной папке `tests\work\`. Успешные тесты не подтверждают подключение к Jira, scopes токена и поведение конкретного workflow.
